# Supabase setup

1. Create a Supabase project.
2. In **SQL Editor**, run the entire `supabase/schema.sql` file, then run `backgrounds/catalog.sql`. If you already ran an earlier version, run the updated files again. The DDL is rerunnable and preserves existing profiles, requests, friendships, notifications, rewards, and encouragement limits. Run it as the trusted project/database owner; the security-definer functions must be owned by a role that can access the underlying tables.
3. Copy `supabase-config.example.js` to `supabase-config.js`, then add the Project URL and **anon/publishable** key from the project's Connect/API settings. Do not use the service-role key in a browser.
4. In **Authentication → URL Configuration**, add the exact local app URL used in your browser (for example `http://127.0.0.1:4173/`) and your deployed Vercel URL (for example `https://your-project.vercel.app/`) to Redirect URLs. Set Site URL to your production domain. The app returns email-confirmation links to the current page.
5. In **Authentication → Providers → Email**, keep email/password enabled. New accounts require a password of at least 8 characters. If email confirmation remains enabled, users must confirm their email before signing in; this is the recommended setting.

The login and registration forms use Supabase Auth for passwords and sessions; passwords are never stored in the app database or browser local storage. On first sign-in, users choose a unique public URL name and receive the starter achievement collections. Profile details, achievement progress, and background preferences are written to that user's `public.profiles` row protected by Row Level Security. Private profile reads and writes are restricted to the owner; public profiles are read through `get_public_profile`, which deliberately omits email addresses.

Run the site through a local web server (not by opening `index.html` directly). For example, from the project folder run `python -m http.server 4173`, then open `http://127.0.0.1:4173/`. Register with an email address you can access, confirm it if prompted, sign in, and complete the profile setup. Existing users can return with the same email and password; their profile, achievement progress, and background preferences load from Supabase. Each public profile is available at `https://your-domain/#/u/your-name`; static hosting such as Vercel can serve these hash routes without additional rewrites. Users can edit their profile and copy its shareable URL from the top-right account menu. Every account receives `cyberpunk.jpg` and `Snowmountain.jpg` as launch rewards; entering `黑神話` in the account menu unlocks `wukong.gif`.

The **兌換背景** field accepts each catalogued file's name, with or without its extension, ignoring letter case; if two files have the same name without extensions, use the full filename. These are client-side codes, not secrets or an admin-only authorization mechanism: any signed-in user can use them.

Background files are stored in `backgrounds`. After adding files, run `node generate-background-catalog.cjs`, run the generated `backgrounds/catalog.sql` in Supabase SQL Editor, and deploy the updated `backgrounds/catalog.js` alongside the images. Static hosting does not automatically expose directory listings. New filenames act as IDs; renaming an asset after users have unlocked it requires an ID migration.

The account menu has **升級背景獎勵**. Each level above level 1 grants one static-image choice, and every multiple of 10 grants an additional GIF choice. Existing users receive credits for their highest observed level, and unused credits are retained when all available items are already owned. Reaching a level again after losing XP does not grant another credit. Claims and inventory notifications are recorded transactionally in Supabase. Like the existing achievement and XP model, level and badge calculations are supplied by the client; these rewards are not an anti-cheat or payment entitlement system.

The profile editor also lets users configure up to two featured showcase cards: a series with an optional note or a list of up to three current interests. These cards are stored in `profile_settings` and are visible on the public profile; the existing schema and `get_public_profile` RPC already include this field. If a featured custom series is deleted, visitors will not see its card and the owner can select a replacement in the editor.

## Friendship backend

The app provides a private roster and notification page, an accepted-friend preview on public profiles, and an encouragement button for friends. Unless stated otherwise the backend RPCs below require an authenticated session and a completed `profiles` row for the caller. A request target must also have a profile. For a shared profile link, resolve its slug using `get_public_profile` and pass the returned `id` as `target_user_id` (not the slug). The caller must sign in and complete profile setup first.

- `send_friend_request(target_user_id uuid)` creates a pending outgoing request. Self-requests and existing pending or accepted pairs fail with an error. If the other person has already sent a request, respond to that incoming request instead; sending back does **not** accept it.
- `respond_friend_request(target_user_id uuid, decision text)` accepts `accept` or `decline` only from the recipient of a pending request, `cancel` only from its sender, and `remove` from either participant of an accepted friendship. Declining, cancelling, and removing delete the relationship, so a new request can be sent later. Invalid decisions, missing relationships, and unauthorized transitions return errors.
- `get_friendships()` returns only the caller's relationships: `peer_id`, `username_slug`, `display_name`, `tags`, `categories`, `status` (`incoming`, `outgoing`, or `friends`), and `created_at` (the original request time). The profile fields are already public via `get_public_profile`; email and profile settings are not included. Results are ordered newest request first.
- `get_public_friends(profile_slug text)` is callable by anonymous and signed-in visitors. It returns up to five accepted friends as `peer_id`, `username_slug`, and `display_name`, ordered by original request time descending, then peer ID. It returns an empty list for an unknown slug or a profile without accepted friends. Pending requests are never exposed.
- `get_public_friend_count(profile_slug text)` is public and returns the total number of accepted friends as an integer, including zero for an unknown slug or a profile without friends. It contains no identities or pending requests; use `get_public_profile` separately to distinguish an unknown slug.
- `send_friend_encouragement(target_user_id uuid)` returns void and sends an `encouragement` notification only to an accepted friend. Each sender can encourage each recipient once per rolling 24 hours; the reverse direction has its own limit. Concurrent attempts are serialized and only one succeeds. The limit persists even if the friendship is removed and later recreated.

The database enforces one unordered pair and no self-friendship. Concurrent requests in opposite directions cannot create duplicates; one succeeds and the other errors. A locked row serializes competing responses and encouragement against removal; acceptance requires a separate action by the recipient. Deleting a profile cascades to its relationships, notifications involving it, and associated encouragement limits. Friendship, notification, and limit table access is revoked from browser roles and protected by RLS; only the RPCs expose or change them, with participant and transition checks inside security-definer functions. Do not grant browser roles direct table access, add permissive RLS policies, or expose a privileged database key. Public previews reveal accepted friendships but never pending relationships.

## Social notifications

These are persistent in-app records, not emails or push notifications. Sending a request creates a `friend_request` for its recipient; accepting creates a `friend_accepted` for the original requester; encouragement creates an `encouragement` for its recipient. Newly acquired badges and backgrounds also create notifications. Background notifications and available badge snapshots are recorded with profile saves; badge state is also synchronized when friendship state loads. The first synchronization records the badges an existing account already has. Decline, cancel, and remove do not create notifications. Existing relationships are not backfilled on schema upgrade.

The header shows the unread total, and the notification page refreshes on sign-in, window focus, and every 30 seconds while signed in. Friend badges depend on the current accepted friend count, may disappear when friendships end, and do not award XP.

- `get_social_notifications()` returns the caller's newest **50** records, sorted by `created_at` descending then `id` descending. Each row has `id uuid`, `kind text`, `actor_id uuid`, `username_slug text`, `display_name text`, `created_at timestamptz`, nullable `read_at timestamptz`, and nullable `detail` for rewards. Actor name and slug are current profile values, not snapshots; no email is returned.
- `get_social_notifications_unread_count()` returns an integer counting **all** the caller's unread records, including older records outside the 50-row list. Do not infer the unread total from the bounded list.
- `mark_social_notifications_read()` returns void and marks **all** currently unread records for the caller as read, including those outside the list. Previously read timestamps are preserved. Notifications arriving concurrently may require another refresh/mark.

Records are historical events: a request notification may remain after cancellation, decline, acceptance, or friendship removal. Consult `get_friendships()` for current status rather than assuming an event is actionable. Records have no automatic expiration or pagination, so older records remain stored but are not returned in the 50-row list; deleting either profile deletes its related records. Separate list and count RPC calls use separate snapshots, so counts can briefly differ during concurrent changes.

### Backend verification

After applying the schema, use three signed-in test accounts with completed profiles (A, B, C), invoking RPCs with each account's own session:

1. A sends to B; A sees `outgoing`, B sees `incoming`, and C sees neither. Repeated and reverse sends fail, as does a self-request. A cannot accept or decline; B cannot cancel; C cannot modify the pair.
2. B accepts; both see `friends` with the same original `created_at`. Pending-only actions now fail. Either participant can remove; both lists then omit the pair.
3. Send again and check B can decline, then send again and check A can cancel. Each deletion allows a fresh request. Missing targets, invalid decisions, unauthenticated calls, and accounts without a profile must fail.
4. Send A→B and B→A simultaneously from separate sessions: exactly one must succeed. Race acceptance against cancellation: only one transition succeeds, and the final state is either accepted or absent. Direct friendship table reads and writes as browser roles must fail.
5. Resolve a shared slug with `get_public_profile`, then send using the returned ID. Verify returned friendship rows contain no email or unrelated users. Rerun the schema and confirm existing relationships remain intact.
6. With more than five accepted friends, verify anonymous and signed-in public previews return at most five accepted peers and the count returns the full total. Pending requests must appear in neither; verify zero and nonexistent slugs too.
7. Check A→B creates one request notification only for B, B accepting creates one acceptance notification only for A, and A encouraging B creates one encouragement only for B. Failed, duplicate, cancelled, declined, or rolled-back actions must not create additional notifications. Historical request events can remain after a relationship changes.
8. Race two A→B encouragement calls in separate sessions: exactly one succeeds. A second attempt within 24 hours fails, including after remove and re-friend; B→A remains separately allowed. Self, non-friend, missing-profile, and unauthenticated calls fail. Race encouragement against removal and check the successful ordering is consistent.
9. Create more than 50 unread events: the list contains at most 50, but the unread count includes all. Mark read and verify the count becomes zero, all older records are also marked, and another user's records are unaffected. Verify direct reads/writes of notification and limit tables fail for browser roles, profile deletion cascades, and schema re-runs preserve existing records and limits. Refresh the list and count independently after changes.
